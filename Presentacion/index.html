Caja Popular

Sistema de gestión de ahorro y préstamos

La Caja Popular es una institución financiera comunitaria que administra el ahorro y otorga préstamos a sus socios afiliados.

El sistema implementa:

  • Alta de socios con validación de edad (≥ 19 años) y aporte inicial (≥ $3,000).
  • Cuentas de ahorro únicas por socio con interés fijo del 20% mensual.
  • Préstamos con tasa del 5% mensual, tope $50,000 y hasta 2 veces el saldo.
  • Máximo 2 préstamos activos por socio.
  • Registro de beneficiarios (1 a 4 sumando 100%) y bloqueo de American Express.

Cada requisito funcional mapeado a su implementación SQL

RF-01 — Edad mínima 19 años

CREATE OR REPLACE FUNCTION check_socio_reglas()
RETURNS TRIGGER AS $$
BEGIN
  IF NEW.fecha_nacimiento >
     CURRENT_DATE - INTERVAL '19 years' THEN
    RAISE EXCEPTION
      'El socio debe tener 19 anios o mas cumplidos';
  END IF;
  RETURN NEW;
END; $$ LANGUAGE plpgsql;

CREATE TRIGGER trg_socio_reglas
  BEFORE INSERT OR UPDATE ON socios
  FOR EACH ROW EXECUTE FUNCTION check_socio_reglas();

Trigger trg_socio_reglas valida antes de cada INSERT o UPDATE en la tabla socios.

7 huecos detectados 7 cerrados Roles + mínimo privilegio

Además: vistas para consulta segura, roles (caja sin privilegios de admin, consulta solo lectura) y REVOKE ALL ON SCHEMA public — nadie tiene más permisos de los necesarios.

En un entorno real, además vigilaríamos:
  • Contraseñas: aquí los password_hash son de ejemplo; en producción irían con bcrypt/argon2 + salt.
  • Datos personales (CURP, RFC): cifrado en reposo y cumplimiento de la Ley de Protección de Datos.
  • Capa de aplicación: consultas parametrizadas para frenar inyección SQL.
  • Conexión cifrada (TLS), base solo en red interna (bind 127.0.0.1 + firewall), backups cifrados y bitácora de auditoría.

Migración — una base, tres motores

La misma Caja Popular, traducida de PostgreSQL a MariaDB y Oracle
PostgreSQL → MariaDB 12.3 + Oracle 23ai

No existe un traductor automático fiable para este caso: herramientas como pgloader migran tablas y datos pero descartan funciones, triggers, CHECK con regex y roles — justo el corazón del proyecto. La traducción se hizo a mano y se verificó en vivo en cada motor.

Resultado idéntico en los tres:

  • 488 filas cargadas — los conteos coinciden tabla por tabla (30 socios, 240 documentos, 80 transacciones…).
  • 48 restricciones activas (28 CHECK, 12 FK, 8 UNIQUE) + 3 vistas.
  • 8 de 8 pruebas de reglas rechazan los datos inválidos igual que el original.

Diferencias de dialecto SQL

¿Cuál motor es mejor?

No hay un único ganador: depende del contexto

PostgreSQL

El más potente y gratuito.

  • + plpgsql muy expresivo
  • + regex y CHECK nativos
  • + estándar, open source
  • − menos "empresas grandes"

MariaDB

El más simple y ligero.

  • + fácil de desplegar (web/LAMP)
  • + rápido, open source
  • + gran comunidad
  • − triggers menos flexibles

Oracle

El más robusto y empresarial.

  • + escala y seguridad bancaria
  • + PL/SQL muy completo
  • − comercial (licencia cara)
  • − pesado y complejo

Veredicto para la Caja Popular: siendo una institución financiera comunitaria, PostgreSQL ofrece el mejor equilibrio (potencia de reglas + costo cero). MariaDB es ideal si se prioriza simplicidad y despliegue web económico. Oracle se justificaría solo si creciera a escala de banco grande con presupuesto y soporte empresarial. Lo importante: la base es portable a los tres.
